# Spec importer: gdd docs → Godot

The Obsidian docs in `gdd/` are the **governing source** for game-piece data.
A markdown file is a spec **if and only if its YAML frontmatter names a `kind`**,
whose value is the Godot class the spec loads as — `Entity`,
`StatusEffect`, `Faction`, `AbilityDefinition`, `Upgrade`, `CylinderShape3D` — spelled as the class is
(`SpecRegistry.KIND_FAMILIES`). An EMPTY `kind:` names nothing, so the doc is not a spec and
is skipped — a stray Obsidian "Untitled" note never blocks an import. An unknown non-empty kind
is a hard error. The importer applies it to the Godot project — one-way (the old Godot→YAML
export direction is retired). The docs themselves have a second writer, the in-game debug
tuning editor, which edits frontmatter values and validates them as this importer would
(`frontmatter_writer.gd`, `gdd/systems/ux/ui/debug-tuning.md`); it never writes a scene.

**One doc per scene.** Two docs naming the same `scene:` is a hard error: each would rewrite
that scene on every run and the import would never converge.

**The file name is the id.** `power_plant.md` is the piece `power_plant` — there
is no `id:` key, and a doc carrying one is a hard error rather than a silent
disagreement with its own name. Consequences worth knowing:

- **Names must start with a lowercase letter and contain only letters, digits,
  and underscores** (`[a-z][a-zA-Z0-9_]*`), since they are ids. Underscores
  separate `<faction>_<role>` components; each component is itself camelCase
  (`an_commandCenter`, `cl_antiInfantry_lightBio`) — plain snake_case still
  matches the same pattern, so old-style ids remain valid.
- **Names must be unique across the whole tree.** Ids share one namespace, so
  two `plant_bomb.md` in different faction folders collide — disambiguate by
  name (`an_plant_bomb.md`), not by folder.
- **Renaming a doc re-keys the piece.** Obsidian updates `[[wikilinks]]` for
  you, but the scene's own `id` property and the generated `EntityIds` const
  follow the new name, and the piece's old scene is left behind carrying a stale
  id — rename or delete that scene by hand.

Doc **location stays purely organizational**: the folder never decides
spec-hood, so a doc can live in any folder under `gdd/` and be moved freely —
faction membership is data, never directory structure.

## Running

```bash
# CLI (headless):
godot --headless -s res://tools/spec_import/import.gd                       # full mode
godot --headless -s res://tools/spec_import/import.gd -- --mode=incremental

# In-editor: the "Spec Import" toolbar menu (addons/spec_import) runs the same
# pipeline and rescans the filesystem afterwards.
```

Pipeline: **scan → validate → sync scenes → generate**. Validation is total
and loud: any unknown reference, duplicate id, or bad enum name aborts the run
**before anything is written** (no fuzzy matching — you reconcile ids by hand,
by design).

**Run it only when the change touches what it READS.** The importer is not part of the
routine test loop — that is GUT (see CLAUDE.md §Running and testing). A run rewrites scenes
and regenerates `scripts/generated/` + `resources/generated/`, so an unnecessary one drags
every doc edit made since the last run into your diff as one wall of unrelated changes, and
buries the change you were actually making.

Run it when the work is doc-facing:

- a piece added, removed, or renamed (its id, its `scene:`, its file name);
- a spec doc's frontmatter edited — stats, `builds:`/`trains:`, `ui:`, weapons, abilities;
- the schema, the validation rules (`spec_rules.gd`), the generators, or the scene sync changed.

Do NOT run it for gameplay code, UI, terrain, navigation, scenario scripting, or test-only
work. Those cannot change what the docs say, so the importer has nothing to tell you — and
its output is noise you then have to explain.

**One caveat when you do skip it:** the generated artifacts may already be stale from someone
else's doc edits, so a piece id you expect in `EntityIds` may be missing. That is a reason to
run the importer deliberately, not a reason to hand-edit a generated file.

**After renaming a piece id, run the importer TWICE.** A rename invalidates the
`EntityIds` constants that hand-written code references, and those constants are
regenerated by the import itself — so the first run executes against a project that
does not compile, and only the second sees a consistent one. It recovers on its own,
but a first run's output cannot be trusted to mean anything.

**A run is only believable when the second one is a no-op.** The sync is idempotent by
design, so "import twice and diff" is the check that it converged; a second run that
still writes something is a bug in the pass that wrote it. It is also how to tell a
real problem from a backlog: if no full import has run for a while, the first one
applies every doc change since as one wall of edits, which looks alarming and is not.

## Scenes are never a prerequisite

Every kind is authored **doc-first**: the importer creates any scene it is
missing, so you can write the markdown and run it.

- **no `scene:`** — the path is inferred (`scenes/entities/<units|structures|
  projectiles>/<faction subdir>/<id>.tscn`), the skeleton is created there, and
  the path is written back into the doc's frontmatter. Available to pieces and
  projectiles, the kinds whose home directory is derivable.
- **`scene:` pointing at a file that doesn't exist** — the skeleton is created
  at that **declared** path (missing directories included). Nothing is inferred
  and nothing is written back, since the doc already holds the path. This is
  the only route for **factions** and **status effects**, which must always
  name their scene.

Skeletons are deliberately bare — a piece is a root of the class its doc derives,
carrying its `id`; an emission is an `Entity` root with its `HitShape`; factions
and status effects are a scripted `Node` — because the sync pass immediately fills in
everything the doc specifies. For a piece that starts with the COMPOSITION pass
(`composition.gd`), which adds every component the doc implies from the component
library in `scenes/components/`; no scene inherits another. Art, collision
shapes, and other non-doc-governed content stay editor work. A status-effect
skeleton is inert: swap in the effect's own script to give it mechanics.

The trade-off: a **typo'd** `scene:` path produces a stray new scene instead of
a validation error. Every created file is listed in the run log — check it.

**The importer cannot hang.** A parse error anywhere in the pipeline used to leave
`_initialize` aborted before its `quit()`, and Godot then span in its main loop
forever — which reads as an infinite loop in the sync and is not one. `import.gd`
now ends the loop after a single frame regardless and exits **1** when it did not
complete, so a broken pipeline fails loudly instead of wedging CI or a terminal.

## Modes

Scalar keys present in a doc always overwrite; **omitted keys never touch the
scene** (that's how visuals/VFX stay hand-authored). The modes only differ on
collection-valued keys (`weapons`, `status_effects`, `trains`, `builds`,
`starts_with`, `sanctions`):

- **full** — the spec list is authoritative: matched items updated, spec-only
  items created, scene-only items **removed**.
- **incremental** — update/create only; scene-only items are preserved.

A second full-mode run immediately after a first is always a zero-diff no-op
(change detection is semantic, against the live component values).

## What gets generated

| artifact | contents |
| --- | --- |
| `scripts/generated/entity_ids.gd` | `EntityIds` — one StringName const per piece, alphabetical |
| `scripts/generated/status_effect_ids.gd` | `StatusEffectIds` consts |
| `resources/generated/technology.json` | cost / build-time / requires per piece and per upgrade (Commander loads at startup) |
| `resources/generated/upgrades.json` | each upgrade's title and `modifies:` entries, ranges resolved to radii (`UpgradeCatalog` loads at startup) |
| `resources/generated/tools.json` | build/train tool registry (Tool loads at startup; command names are `command_tool_<id>`) |
| `resources/generated/debug_roster.json` | every placeable piece (units, structures, features, plus undocumented piece scenes) for the debug spawner — see `gdd/systems/ux/ui/debug-mode.md` |
| `resources/generated/families.json` | every `family:` and its members' template data (footprint, hp, price, build time, infrastructure) — read through `PieceFamilies`; see §Families and variants |
| `resources/generated/shapes/<id>.tres` | one `CylinderShape3D` per shape-library doc; written BEFORE the scene sync, because scenes reference them |

`Entity.id` (a StringName) replaced the old `Entity.Type` enum; hand-written
code references pieces via the generated `EntityIds` consts.

Before any of it is written, the command-grid buttons the docs author are reviewed, and two in
one cell that could be on screen together fail the import, naming both docs
(`SpecGenerators.grid_collisions`; why: `gdd/systems/ux/ui/command-card-and-hotkeys.md`).

## Doc schema

Two keys are common to every kind:

- **`kind`** (required — it's what makes the doc a spec) — the CLASS the spec
  loads as, in `PascalCase` because it is a class name. It says nothing about what
  a piece IS: every game piece is `kind: Entity`, and whether it is a unit or a
  structure, built or trained, is derived from its components (`footprint:`,
  `movement:`). The old design-category values (`unit`, `structure`, …) are refused
  with the replacement named. The **file name** supplies the id, which is the stable
  game-side key: keep it **generic**, flavor-neutral (e.g. `anarchical.md`, not
  `baladians.md`), because renaming the file ripples through generated code and
  cross-references.
- **`title`** — the user-facing display name (flavor text). Named `title`, not
  `name`, because `name` is reserved on Godot nodes. For a **faction** the title
  is written to the scene's `faction_name`; for a piece with a `ui:` key it is
  **the text on its command-grid button**, and is also carried as display
  metadata (e.g. the balance tool's roster name). A piece has exactly ONE display
  name: there is no `ui.label`, and a doc carrying one is a hard error. A piece
  in the grid with no title — or with a title that just repeats its id — is
  WARNED about and shows the raw id on its button.
- **`editor_description`** (optional) — copied verbatim into the scene root
  node's Godot-native `editor_description` (the in-editor tooltip). Multi-line
  values are fine.

Wikilinks are accepted anywhere an id is expected (`"[[warlord]]"`,
`"[[dir/warlord#Stats|alias]]"` → `warlord`). Times are **seconds** (converted
to 30 tps ticks on import). Enum names come from the engine enums
(`Defense.ArmourType`, `Defense.FrameType`, `Damage.Type`, `Movement.Mode`), and
the emission motion presets from `EmissionPhase.PRESETS`.

### The canonical key order, and the nests

**A spec doc's SHAPE is part of the schema, not decoration.** Keys are grouped by
what owns them — one top-level key per component, its sub-keys that component's
authored values — and the grouping IS the order, because a doc is read top to
bottom. The rationale is `gdd/systems/authoring/spec-importer.md` §The doc's shape;
`tools/spec_import/schema.gd` (`SpecSchema`) is the order and the nests as code.

**Order is never a validation failure.** A doc whose keys are out of order imports
normally, and the importer **rewrites its frontmatter into canonical order in the
file** — in the same pass that writes an inferred `scene:` back, because `gdd/` is
an Obsidian vault under Sync and a second visit races the editor. The rewrite is
held to three properties, each of which is a way it could otherwise eat a doc:

- **Idempotent** — reordering an already-ordered doc changes no bytes, so a doc
  that needs nothing is not written at all. This is the same "a second run is a
  no-op" test the scene sync is held to.
- **Total, in both directions** — an unknown key is never dropped. It sorts to the
  end of its own level, in the order it was authored, where it is visible.
- **Comment- and value-preserving** — whole key blocks move; values are never
  re-serialised, so block scalars, wikilinks, flow collections and multi-line
  strings round-trip byte for byte. A comment travels with the key below it.

Anything the rewrite does not understand — a level with irregular indentation, a
sequence item whose first key would land behind a comment — is left EXACTLY as
authored. Leaving a doc unordered costs nothing; corrupting one costs a file.

A **sequence's item order is data** and is never touched: the first weapon is the
first weapon. Only the keys inside each item are canonicalised.

### kind: Entity

A game piece. Its role is DERIVED from what it declares: `footprint:` makes it a
fixture (built, occupying the grid), `movement:` makes it mobile (trained), and a
piece may declare both — the two-form piece, built unless a producer's `trains:`
names it. A piece declaring neither, nor `senses.vision:`, is refused: it has no
body and no sense, so it is prose carrying the marker or a doc missing its key. A
new scene is composed from those same keys (`composition.gd`): `movement:` brings
locomotion, `footprint:` a `Fixture`, and a piece with both gets both.

```yaml
# file: an_bioLight_builder.md   <- the file name IS the id (no id: key)
kind: Entity
title: Irregular               # user-facing display name (flavor text)
scene: res://scenes/entities/units/an/an_bioLight_builder.tscn   # optional; created if missing
editor_description: Guerilla infantry; builds structures.  # optional -> Godot editor_description
commandable: false             # OPT-OUT only; see below. Omit it on almost every piece

flavor:                        # the player-facing HUD copy
  description: Guerilla fighter that builds structures, effective in numbers
  verbose: >-
    Cheap and strong in numbers, effective against other infantry.

build:                         # the macroeconomic transaction
  cost: {energy: 250, infrastructure: 0, dominion: 0}   # defaults to {energy: 100} when absent
  time: 20                     # seconds; defaults to 10 when absent
  requires: [an_warFactory]    # structure ids; ALL must be built to unlock
  completes_as: UNIT           # what a BUILT piece stands up as; defaults to STRUCTURE

defense:                       # -> Defense
  hp: 160                      # Defense.hp_max
  armour: MEDIUM               # Defense.ArmourType
  frame: BIO                   # Defense.FrameType

senses:                        # -> the detection volumes on the root
  vision: vision_ground_small  # a shape-library id. 0 / false / LEFT EMPTY opts out
                               # (no aggro: key — it is derived from weapon reach at
                               # runtime, per layer; see combat/range-buckets)
  detection: detection_small   # library id it sees THROUGH stealth with; creates a
                               # DetectionRange volume. 0 / false / left empty opts out

body:                          # -> the physical volume on the root
  radius: 0.3                  # MovementBody radius (nav footprint / avoidance). The
                               # hurtbox is not a key: the importer fits it to the model
                               # (gdd/systems/ux/ui/generated-visual-defaults.md)

movement: {speed: SLOW, turn_rate: 1080}   # speed NAMES a class — see kind: SpeedLibrary
# ...and the rest of the chassis. EVERY movement sub-key is validated against
# SpecRegistry.MOVEMENT_KEYS, so a typo is a hard error rather than a silently
# ignored line — that omission is how four of these came to live only in scenes.
#   max_acceleration: 3.0        # world-units/s^2, positive; INF (unbounded) by default
#   max_deceleration: -3.0       # world-units/s^2, NEGATIVE — a signed floor, not a magnitude
#   crush_class: MEDIUM          # Movement.CrushClass, by name
#   min_turn_speed_ratio: 0.0    # 0..1; GROUNDED only. 0 pivots in place, 1 arcs at speed
#   reverse_speed_ratio: 0.35    # 0..1; HOVERING only
# A key belonging to one mode and set on another is REFUSED, not ignored: the value
# would be inert (an orbit on a ground unit is read by nothing), and inert is
# indistinguishable from tuned until you go and find the branch that consumes it.
# The mode itself is not a movement key: a piece that flies says so under `aerial:`,
# and one that does not names no mode (GROUNDED). `movement.mode`, `docks` and the
# orbit keys are refused with a pointer to where they went.
aerial: {mode: FLYING}         # the Aerial component — its presence makes an aircraft
#   mode: HOVERING | FLYING      # required; GROUNDED is not a way of flying
#   orbit_radius: 3.0            # FLYING only. Derived, and refused here, when a weapon has
#                                # `range_from: orbit`: it is that weapon's ground reach
#   orbit_speed: SLUGGISH        # FLYING only. Names a speed class, like movement.speed
docking: true                  # the Docking component — the piece docks at airfields.
# Presence only; absent = does not dock (the kamikaze drone, expended on its first run).
# Needs `aerial:` (a ground unit that docks is not built yet). A charged weapon on a piece
# without it is a hard error — its clip could never be refilled.
footprint: [3, 3]              # structure-only: Structure.dimensions (grid cells)
weapons:                       # matched by name (the sync key)
  - name: Rocket
    emits: warlord_rocket      # emission id; omit for a melee weapon:
    # melee_damage: 10
    # melee_damage_type: LEAD
    split_time: 1.5            # seconds between attacks
    reload_time: 1.5           # seconds to restore a FULL clip
    startup_time: 1            # seconds a target must be held before the first shot;
                               # kept through a reload. Omitted = 0 (Weapon.startup_time_ticks)
    clip_size: 1
    charged: false             # true = never reloads in the field; must dock at an
                               # airfield, which takes reload_time. See the charged-
                               # ammunition section of CLAUDE.md. Requires docking: true.
    turret: true               # aims on its own yaw, so the body need not turn to face
                               # its target (Weapon.turret). Omitted = false.
    turret_turn_rate: 360      # turret swing speed, degrees per second. Only with
                               # turret: true. Omitted = the Weapon default (360).
    range_from: hull           # where reach is measured from (Weapon.RangeOrigin): hull =
                               # footprint to footprint; orbit = the range shape standing at
                               # the centre of the piece's orbit, overlapping the target's
                               # hurtbox. orbit needs aerial: {mode: FLYING}. Omitted = hull.
    reach: {ground: ground_range_medium, air: air_range_long}   # shape-library ids, or
                               # one id for every layer. Never a number — see kind: ShapeLibrary
    hits: [ground, air]
trains: [an_bioMedium_dominionGen]   # Production.producible_types
builds: [an_barracks]          # Builds.buildable_types (builder units use this too)
variants: [nt_building_square, nt_building_long]   # the family members this piece is built FROM,
                               # default first; see §Families and variants
family: neutral_building       # membership of a named piece family (SpecSchema.FAMILIES)
# What this piece HOLDS. Two independent halves, as in the Garrison component: who may
# enter (three enum lists -> occupancy bitmasks) and how much room (capacity counts
# OCCUPANCY, not heads). Only keys you name are written; `garrison: false` removes the
# component, and `garrison: true` is refused (say `{}` to take every default).
garrison:
  capacity: 8                  # total occupancy, not a head count
  frames: [BIO, MECH]          # Defense.FrameType     — default: both
  armours: [LIGHT, MEDIUM, STRONG]  # Defense.ArmourType — default: all
  movements: [GROUNDED] # Movement.Mode, same spelling aerial.mode uses
  closed: true                 # the CLOSED HOLD: every mask cleared, so nothing can be
                               # ordered in or out (a stock truck's cage).
                               # Mutually exclusive with the mask lists and with `pieces`
  bunker: true                 # occupants fire out
  preserve_occupants: true     # occupants are released rather than killed when it dies
  range_bonus: {from: ground_range_medium, to: ground_range_long}
                               # extra reach for occupants firing out: the gap between two
                               # reach buckets, never a number
  reach_by_piece: {lb_mechLight_antiLight: ground_range_long}
                               # the reach one occupant piece fires out with, in place of
                               # its own (never shorter than its own)
  pieces: [an_bioLight_builder]         # ALLOWLIST of piece ids, checked on top of the three masks.
                               # Omitted = no identity restriction (NOT "nobody" — unlike a
                               # mask, an id list can never be exhaustive)
  sentence_length: 45                   # a captive DEPOSITED here serves this many seconds,
                               # paying dominion per cycle, before being CONSUMED. Naming it
                               # (a positive number) is what makes a garrison a prison
                               # (Garrison.can_intern) — DEPOSIT offers no other target. The
                               # Compound is the case: `closed: true` (deposit is the only way
                               # in) plus `sentence_length:`, and no `pieces:` — a captive
                               # is held as itself, never converted
  unload_time: 1               # a CARRIER's seconds per captive when it deposits: the first
                               # goes over when the deposit completes, one per interval after.
                               # Omitted = the whole load at once
abilities:                     # the abilities it can use, and the charge pools they share
  - {cooldown: 60, grants: [beacon]}
repairs: true                  # gives the piece a Repairs component; omitted = cannot repair
stealth: true                  # gives the piece a Stealth component (presence is the whole
                               # mechanic — the component has no exports)
shelter: true                  # identity components, by PRESENCE only — also
                               # extraction_site / extractor / plants_beacons (a spotter that
                               # plants a ground beacon and leaves, rather than holding one);
                               # tuning stays in the scene
beacon: 20                     # persistent bombardable bubble (BeaconRange); false removes
infrastructure: -40                    # Actor.infrastructure: >0 provides, <0 consumes, 0 neutral
occupancy_size: 2              # how much of a garrison's capacity this piece consumes
                               # when garrisoned (default 1)
ui: {grid: [1, 2], factions: [anarchists]}   # button text is `title`; no label key
exceptions: {}                 # the calibration waiver block — always last
```

Three keys in there are newer than the rest and have no consumer in the game yet;
they exist so the schema can state what the composition rework needs
(`gdd/systems/authoring/composition-rework.md`), rather than being rewritten a
second time when it lands.

- **`commandable:`** — whether the piece answers to orders. It has **no fixed
  default** and is **DERIVED**: a doc that declares a body the player owns and acts
  through (`footprint:` or `movement:`) is commandable, and a doc that declares a
  payload is not. So the key is only ever an OVERRIDE, and there are exactly two
  uses for it: `false` on something with a body that answers to nothing (the
  deposit), and `true` on something without one that takes orders anyway (a unit a
  weapon emitted). A flat default cannot be chosen — `true` would make every bullet
  commandable and `false` every barracks inert.
- **`build.completes_as:`** — what a BUILT piece stands up as once construction
  finishes; `STRUCTURE` unless a doc says `UNIT`. `Build` can only ever raise the
  deployed form (it reserves footprint cells and punches a navmesh hole), so this
  names what happens AFTER that — the one part the origin cannot know. The default
  is conservative in the literal sense: it is what every piece in the roster does
  today, so adding the key changed nothing.
- **`exceptions: {has_mesh_visual: <why>}`** — the opt-out from the default model. It
  is a WAIVER of the `ASSET` rule that a piece carries a model, so it goes `STALE` —
  failing the import — once the scene holds authored art; the rule reads the scene for
  that (`SpecRegistry._asset_facts`). Unwaived and without art, the piece is reported as
  an unfilled slot (`PLACEHOLDER`), never an error. The same waiver shape opts a unit out
  of `has_voice_lines` or `has_death_sound`. It **removes as well as refuses**: a pass that
  only declines converges from one direction, so declaring it deletes the placeholder
  model already in the scene. An emission may declare it too. `visual:` was the
  earlier spelling and is refused. What it reaches today is that generated
  placeholder. PLANNED (composition-rework step 5): now that `MeshVisual` is the
  piece's own node rather than an inherited one, the waiver can remove it too.


- **Every doc-governed shape is a `CylinderShape3D`** of a fixed height
  (`SpecSceneSync.SHAPE_HEIGHT`, 100), so a spec authors only the radius —
  `senses.vision`, `body.radius`, and each
  shape-library entry (which a weapon's `reach` names). The height is deliberately far taller than the world: shapes sit at
  the entity's origin, so vertical separation (aerial units cruise at
  `Aerial.AERIAL_HEIGHT`) never decides an overlap. A shape authored as some
  other type in the editor is REPLACED by a cylinder on the next import, not
  resized, so the doc always wins. (Shape type is not parameterizable yet.)
- **`repairs:`** is a bare bool, not a list, because presence of the `Repairs`
  component IS the capability — the Repair command asks nothing else of the
  actor, and which targets it applies to is a property of the TARGET (friendly,
  MECH-framed, finished, damaged). `true` creates the component, `false` removes
  one the scene owns, and an omitted key leaves the scene alone like every other
  spec key. The repair RATE is scene-authored (`Repairs.repair_rate`) and not
  doc-governed yet.
- **Every component key can remove its component.** `repairs: false`,
  `stealth: false` and `garrison: false` remove theirs, as do the radius keys where
  zero disables (`senses.vision`, `senses.detection`, `beacon` — the
  same statement as `: 0`). The four COLLECTION keys — `trains`, `builds`,
  `weapons`, `status_effects` — remove theirs with an **empty list**: "trains
  nothing" and "is not a trainer" are one claim, so `trains: []` takes `Production`
  away and naming a trainee later brings it back. `false` is refused on those four.
  `true` is REFUSED everywhere for the reason `garrison: true` is: a list and a
  radius have no defaults to take, so a bare true would silently adopt whatever the
  scene already held.

  **On those radius keys an EMPTY value says it too** — `vision:` with nothing after
  it is the same removal as `vision: false`. That is the spelling an author actually
  produces, by deleting a number rather than the line, and refusing it made the
  ordinary way of taking a volume away an import error. It stays refused where zero
  does not disable (`body.radius`, a projectile's `blast`): those
  volumes are not optional. Emptiness means removal only for these keys — elsewhere
  an empty value is still whatever that key's own validation says it is.

  An **empty list is not the same statement**: `trains: []` is a trainer that
  trains nothing and keeps its `Production`, while `trains: false` deletes the
  component. An **omitted** key still touches nothing at all.

  Removal is total — the node, its descendants, and every `ext_resource` /
  `sub_resource` the removal orphaned, so that creating a component and then
  removing it gives the file's earlier bytes back exactly. See
  `gdd/systems/authoring/composition-rework.md` §Step 0 for why that identity is
  load-bearing, and `tests/test_TscnDoc.gd` for the contract as tests.

  An emptied (or `false`) `senses.vision` is the same removal: the
  `VisionRange` node goes, and composition never adds one to a piece whose doc
  switched vision off. Tests: `tests/test_SpecShapeRemoval.gd`.
- `ui:` makes the piece buildable/trainable (it becomes a Tool registry entry).
  `ui.factions` is **button-grid layout metadata** for the collision review,
  not a gameplay gate — availability is always technology (structures owned).
  The button's TEXT is the doc's `title` (no `label` key — see above), and its
  two hover tooltips are SYNTHESIZED from this same frontmatter: a one-line
  "Build Redoubt — 500 energy, 10s", and a full stat readout for the held verbose
  key (see `VerboseTooltipButton`). So a rebalanced or renamed piece re-describes
  its own button with no code or scene edit. Optional `ui.tooltip` /
  `ui.verbose` override either tier with authored words.
- A doc **without** `scene:` gets a skeleton scene created (composed from the
  component library, placeholder art from the visual-defaults pass), and
  the new path is written back into the doc's frontmatter. Scene placement maps
  `gdd/factions/anarchical/` → `an/`, `colonial/` → `cl/`. A doc **with** a
  `scene:` whose file is missing gets the same skeleton at that exact path —
  see [Scenes are never a prerequisite](#scenes-are-never-a-prerequisite).

`beacon:` and `spotting:` drive the Colonial bombardment components (see CLAUDE.md
§The Colonial bombardment system). `beacon:` carries no `_range` suffix for the same
reason `senses.detection` does not: it is a bare radius, and the suffix was noise.
The GUN half is not a component key at all: a battery is an ABILITY, so the doc that
says a piece can bombard is its `abilities:` block.

`spotting` is a bare bool — the same shape as `repairs:` and `stealth:` — because
presence IS the capability and the component has no exports left. A spotter's
reach and channel are `Spotter.TARGET_RANGE` / `Spotter.CHANNEL_TICKS`,
**constants rather than per-piece numbers**, because exactly one piece in the
game spots and a value that never varies is not a configuration: exporting it
makes the inspector claim a choice nobody makes, and makes this schema govern a
number with one possible value. Give the component its exports back, and this key
a `{range:, delay:}` mapping, on the day a second spotter exists. The old mapping
form is a **hard error**, not an ignored key — a doc carrying it believes it is
setting a reach.

**`bombards:` is retired**, and a doc still naming it is a hard error pointing at
`abilities:`. A battery was a cooldown plus a per-use projectile driven by one
command, which is what an ability already is: the reload is a one-charge pool on the
gun, and the shell is the ability's `emits:`. See
`gdd/systems/combat/bombardment.md`.

`abilities:` gives the piece an `Abilities` component — the abilities it can use,
grouped into the charge pools they SHARE. (It was `ability_groups:`; the `_groups`
suffix described the YAML's shape rather than the component's.) Every id in a
`grants:` list is a `kind: AbilityDefinition` doc, whatever unlocks it — a piece can be granted
an ability it pays dominion for, one it gets free, and one bought at a structure, and
the pool cannot tell them apart because it does not care.

```yaml
abilities:
  - max_charges: 1                # pool capacity; optional, defaults to 1
    initial_charges: 0            # stock when the piece is built; optional, defaults to max_charges
    cooldown: 60                  # seconds to regain ONE charge
    grants: [beacon, freeze]      # ability ids; every id here draws on this pool
```

Capacity and starting stock are separate keys because they answer different balance
questions: `max_charges` is how much the ability holds, `initial_charges` is whether a
freshly-built piece comes online armed. `initial_charges: 0` means "available one cooldown
from now" — the pool starts counting down immediately. Capacity may not be zero (an
ability that is "just a cooldown" is a one-charge pool, not a second mechanic); starting
stock may. Every `grants` id is checked against the ability registry, and no ability may
appear in two pools of one piece — "which charges does it spend?" would otherwise depend
silently on list order. The older single `charges:` key is a **hard error**, not an alias.

**A piece that prices nothing gets a placeholder**, not nothing — units and
structures alike: `SpecRegistry.DEFAULT_PIECE_COST_ENERGY` (100 energy) and
`DEFAULT_PIECE_BUILD_TIME_SECONDS` (10s), filled in at registration so
`technology.json`, the button tooltips and the Scavenge kill bounty all read the
same number. A doc naming either key keeps exactly what it says, and a partial
`build.cost: {infrastructure: 5}` counts as priced (that piece deliberately costs no energy).

An absent `build.cost:` therefore no longer means "not buildable" — it means
"buildable at the placeholder price". Nothing becomes PURCHASABLE by that alone:
a piece is only offered if it has a `ui:` grid button or sits in some producer's
`trains:` list, so neutral map furniture (`nt_extractionSite`, `nt_building_*`,
`nt_shelter`, `nt_bioLight_terrestrial`) is priced but unbuyable.

### Families and variants

**`family:`** names a set of pieces that code enumerates or recognises as one thing without
matching on ids. The value is one of `SpecSchema.FAMILIES` (today `neutral_building`, the
`nt_building_*` pieces); anything else is an error, and a member must be a structure. The
importer writes the family name as a **group** on every member's scene root, publishes the
members and their **template data** — footprint, hp, energy cost, build time in ticks and
`infrastructure` — in `resources/generated/families.json`, and `PieceFamilies` reads it back.

A family member is a TEMPLATE, so its `infrastructure:` is published there and is **never
written to the scene root**: `Actor.infrastructure` is credited to whichever commander owns
the node, and a neutral (or garrison-captured) building must grant nothing.

**`variants:`** lists the family members a piece is built from, default first (Anarchical
`an_infrastructure` lists `[nt_building_square, nt_building_long]`). Each entry must be an existing
structure that has a `family:` and no `variants:` of its own — anything else fails the import. The
piece takes its footprint, hp, cost, build time and infrastructure from the FIRST variant, so its
doc must not author them (an authored copy is an error) and the composed scene, its technology price
and its tool tooltips describe the default variant. The list is published as `variants` on the
piece's `tools.json` entry (`Tool.variants`); which variant a build uses is a runtime choice.

### Emissions (`kind: Entity` with emission keys)

An `Entity` doc naming any emission key (`phases:`, `speed:`, `trajectory:`,
`damage:`, `damage_type:`, `blast:`, `hitscan:`, `status_effects:`) is an
emission: its scene is an `Entity` root with a `PhasedLocomotion` and a `Payload`
(`SpecComposition.EMISSION_COMPONENTS`). It may not also declare `footprint:` or
`movement:`. `kind: Projectile` is retired.

```yaml
# file: radiation.md
kind: Entity
scene: res://scenes/entities/projectiles/radiation.tscn
damage: 3                      # Payload.base_damage
damage_type: LEAD
hitscan: false                 # the AIMING rule: true = the named target, false = the HitShape
blast: aoe_medium              # optional: an aoe_* library shape (omit = single target)
status_effects: [lazer_burn]   # status-effect ids -> instanced scenes under EffectApplicator
phases:                        # or the shorthand: speed: + trajectory: (see below)
  - motion: {preset: BALLISTIC, speed: FAST}
  - lifespan: 10
    payload: 0.5
```

An emission is an ordered list of **phases**, each a motion, its end clauses, a
payload cadence and optional events. The grammar is
`gdd/systems/combat/projectiles.md` §Phases. Without `phases:`, `speed:` and
`trajectory:` are a **shorthand** for the common shape — a flight that ends on
arrival, then one tick that applies the payload. The trajectory is a preset name
(`LINEAR`, `BALLISTIC`, `LOFTED`, `HOMING`); a steered one (HOMING) needs a
lifespan, so it is written as `phases:`. The importer writes one `EmissionPhase`
node per phase on the scene itself.

**Every motion value is in human units** — `speed:` NAMES a speed class (see
`kind: SpeedLibrary`), from the same ladder as `movement.speed`, which is what you are
really comparing it against ("does this rocket outrun the tank it is chasing?");
lifespans and cadences in seconds. The scene stores the same units, and `EmissionPhase` converts to ticks at
use.

`blast:` sizes the projectile's `HitShape`, and that ONE number decides both what
takes damage and what receives the `status_effects:` — `Payload.apply`
resolves the overlapping entities once and uses that set for both, so the two can
never disagree. Friendly units in the radius are included. Omitting the key leaves
the scene's shape alone, so hand-authored blasts are untouched; it is rejected
alongside `hitscan: true`, which resolves onto one target and never consults the
shape at all. The importer REMOVES a hitscan emission's `HitShape`, so the
shape's presence is the blast (`Payload.has_blast`).

A projectile can also be written **inline**, as an `emits: {...}` mapping on the
weapon that fires it; the importer hoists it into a normal registry entry. An
inline projectile is the one place an `id:` key is still used — it has no file of
its own to take a name from, so the key names it (defaulting to
`<piece>__<weapon>`):

```yaml
weapons:
  - name: Rocket
    emits: {id: rifle_round, damage: 5, damage_type: LEAD, speed: SUPERSONIC, trajectory: LINEAR}
```

`weapons[].emits` is a **doc-key rename only** — `projectile:` was its previous
spelling, and a doc still carrying that is a hard error. The property it writes is
still `Weapon.projectile_scene`.

### kind: StatusEffect

```yaml
# file: lazer_burn.md
kind: StatusEffect
scene: res://scenes/entities/status_effects/lazer_burn.tscn
```

Registration only: the effect's mechanics stay authored in its scene/script;
the doc just makes the id referenceable from projectiles (and enumerated in
`StatusEffectIds`). Like a faction, it must name its `scene:` but the file need
not exist — a missing one is created as a bare `StatusEffect`-scripted `Node`.
That skeleton does nothing until you point it at the effect's own script (e.g.
`damage_over_time_status_effect.gd`), since there is no sync pass for this kind.

### kind: Faction

```yaml
# file: anarchical.md         <- generic ideology id
kind: Faction
title: Anarchists              # user-facing name -> scene faction_name
scene: res://scenes/factions/anarchical.tscn
starts_with: [warlord, irregular, irregular, irregular]   # units only; the command centre is
                                                         # dropped (Deployment), never listed
sanctions: [ambush, dignify, informant, scavenge]   # kind: AbilityDefinition docs with a dominion route
```

Unlike pieces, a faction doc must always name its `scene:` — but the file need
not exist yet. When it is missing, a skeleton `Faction` scene is created at
that exact path, then filled in from the doc like any other faction scene. So
a new faction is authored doc-first: write the markdown, run the importer, get
a working scene.

`sanctions` is the faction's DOMINION SHOP: the **ability docs** (`kind: AbilityDefinition`,
below) whose `column:` / `levels:` fill its sanction grid — not individual cells. The
whole grid is rebuilt from them, in the order listed. Naming an ability that authors
no `levels:` is an error: it has no cells to draw.

### kind: AbilityDefinition

An ABILITY is a thing a piece can do. What it IS lives here; WHO can use it and how
often is the piece's `abilities:` block, because the charge pool belongs to whoever
holds it.

```yaml
# file: ambush.md           <- one doc per ability
kind: AbilityDefinition
title: Ambush              # the ability's name (its levels carry the cell names)
flavor:
  description: One line, for a HUD button that has no cell to take copy from.
  verbose: |
    The held-key tier of the same.
passive: false             # never emitted through a command; standing while owned (default false)
hud_button: false          # does it get a button on the top bar? (default false)
command: command_bombard   # the grid command its HUD button arms; sanction-unlocked abilities
                           # are armed as their own cell instead, so the two are alternatives
cast_by: SINGLE            # how many SELECTED casters fire it with no modifier held:
                           # SINGLE (the default) or ALL. See below
emits: cannon_shell        # the piece it throws per use (a `res://` scene path is also accepted)
column: 0                  # 0-based sanction grid column — THE DOMINION UNLOCK ROUTE
levels:                    # its cells, in CHAIN order. Absent = not unlocked with dominion
  - title: Ambush 1        # the cell's name, and how it matches the scene
    tier: 1                # 0-based row; must DESCEND down the list
    cost: 250              # dominion
    cooldown: 60           # seconds
    description: Drops 4 × {{ an_bioLight_builder }} at the target point.
    verbose: |             # the held-key tooltip tier; block scalars are fine
      Longer copy, as many paragraphs as you like.
    needs_vision: true     # may it be aimed into the shroud? (default true)
    needs_target: true     # is it aimed at all? (default true)
    kill_bounty: 0.1       # standing benefit; requires the ability to be passive:
  - title: Ambush 2
    tier: 2
    cost: 500
```

**`column:` and `levels:` are the DOMINION UNLOCK ROUTE, and that is now the whole
meaning of "sanction".** An ability that authors neither is not a sanction: it is
free (the Bombard's battery — owning the gun is the unlock), or bought at a structure
through the ordinary purchase queue. Nothing else about the ability changes with the
route.

**`passive:` and `hud_button:` sit at the doc's top level, not on a level**, because
both are facts about the ability itself: Scavenge 2 is not more passive than Scavenge
1, and an ability does not earn a HUD button by being upgraded. A `passive:` inside a
level is a hard error naming the top-level key.

A PASSIVE ability is never emitted through a command — it is attached to the piece
and present persistently, like the Anarchists' Scavenge bounty — so it has no aim
point, no cooldown and no button.

**`hud_button:` decides HUD presence, and it defaults to false.** It used to follow
from being dominion-unlocked, which conflated the HUD with the shop: an ability
nobody paid dominion for could not have a button however far it reached. The rule of
thumb for setting it is REACH — an ability whose effective range is global wants one,
because the player cannot walk the map to find a caster. The button selects every
piece that can use the ability and arms it, leaving one right-click to aim.

A doc with `levels:` is one **family** — a chain running down one column, where each
level continues and **supersedes** the one above it. `parent` is never written by
hand: it is the level ordering.

A family is **not** the same thing as a column. Several unrelated abilities may share
a column (the Colonials' Gunship sits under Scan 3 without continuing it); those are
**separate docs carrying the same `column`**. Sharing a column is layout; being a
level is a dependency.

`{{ piece_id }}` in `description` / `verbose` renders as that piece's `title`,
resolved **at import**, so the scene carries finished prose and renaming a piece
re-renders every ability that mentions it. An unknown id is a hard error.

**What stays in the scene** is the payload: `Sanction.event_scene` and the bot's
aiming knobs (`targeting`, `effect_radius`, `min_targets`). A sanction's
behaviour is an event scene, which is not a value anyone can type into YAML — so
the doc carries the numbers and the prose, and the doc BODY carries the
human-readable spec for the mechanic itself.

A cell a doc declares and the scene lacks is **created**, pointed at
`sanction_stub.tscn` — an unimplemented sanction should be a visibly inert cell,
never a null `event_scene` (which arms a button that then never disarms). In
full mode a scene cell no doc names is **dropped** from `sanction_unlocks`.

**`cast_by:` defaults to SINGLE, and that default is the interesting half.** With a squad
selected, one click on a point spends ONE caster's charge — because the alternative spends
every caster's charge on the same target, and a charge pool is the scarce thing an ability is
balanced around. `cast_by: ALL` is for an ability whose value is in everyone applying it at
once; `spot` is the roster's only one, since a second firing solution on the same ground is
worth having. Either way the player overrides per click: `modifier_narrow` always sends one,
`modifier_broaden` always sends all (see
[ui/control-matrices](../../gdd/systems/ux/ui/control-matrices.md) §Cast arity).

A **passive** naming `cast_by:` is a hard error rather than an ignored key: nothing casts a
passive, so the doc reads as though the ability were active and the author has misunderstood
one of the two.

Every ability doc also produces an entry in **`resources/generated/abilities.json`**,
read at runtime by `AbilityCatalog`. That is where a free ability's definition lives —
a dominion-unlocked one additionally has its per-CELL copy baked onto the faction
scene's `Sanction` sub-resources, which is why the two carry different things.

### kind: Upgrade

An UPGRADE is one-time, commander-wide research, bought at a structure. The rules are
[`gdd/systems/macroeconomics/upgrades.md`](../../gdd/systems/macroeconomics/upgrades.md).

```yaml
# file: advanced_targetting.md    <- the upgrade's id, in the one shared namespace
kind: Upgrade
title: Advanced Targetting
flavor: {description: Recruits call in firing solutions from much farther away.}
build:
  cost: {energy: 800}             # required: an upgrade is never priced by default
  time: 45                        # required, seconds
  requires: []                    # optional structures, as for a piece
modifies:                         # required, at least one entry
  - piece: cl_bioLight_antiLight  # must be granted `ability` by its abilities: pools
    ability: spot
    range: ground_range_siege     # a shape-library id; generated as its radius
ui: {grid: [0, 2], factions: [colonial]}   # required: row 2 of the researching structure's card
```

It is researched wherever a structure lists it: **`researches: [advanced_targetting]`** on the
structure's doc. That key gives the structure a `Production` component (or extends the one its
`trains:` already gives it), because a research job runs in the same global queue as training.

Validation refuses any other top-level key, an empty or absent `modifies:`, a modifier on a
piece that is not granted the ability, and a `researches:` entry that is not an upgrade. An
upgrade nothing researches is a warning, since its button can never be drawn.

A modifier selects by `piece:` or by `frame: BIO|MECH` (every unit of that frame), and carries
exactly one effect: `range` (a shape id; needs `ability:`), `hp_factor`, `rearm_rate_factor`
(the piece must carry a `charged:` weapon), `cooldown_rate_factor` (needs `ability:`) or
`unlocks: true` (needs `ability:`; the ability is locked for that piece until researched). A
factor is a positive number, 1.25 meaning a quarter more. The effects are
`SpecRegistry.MODIFIER_EFFECTS`; a new one is added there together with the runtime reader
that honours it. What each one does: the upgrades note §What an upgrade can change.

### kind: ShapeLibrary

The **shape library**: named shapes that `reach:`, `senses.vision:`, `senses.detection:`
and an emission's `blast:` point at, so each comes in a few shared buckets instead of one
number per piece. A bare number is refused on all four. Changing a bucket is one edit, and
everything in it follows.

The whole library is ONE doc, `gdd/shapes/shapes.md`, so every bucket can be read and tuned
side by side. Each entry of its `shapes:` mapping is one shape: the key is the id specs
name (in the same namespace as every other spec id), the value its keys. An entry's `kind:`
is `CylinderShape3D` (the default) or `SphereShape3D`, which takes a radius only.

```yaml
# file: gdd/shapes/shapes.md
kind: ShapeLibrary
shapes:
  ground_range_medium: {radius: 5}
  aoe_small:           {kind: SphereShape3D, radius: 1}
```

`kind: CylinderShape3D` / `kind: SphereShape3D` as a doc's OWN kind is retired: a shape
is an entry, never a file. A cylinder may name a `height:`; without one it is
`SHAPE_HEIGHT` like every other doc-governed shape. Each entry generates `resources/generated/shapes/<id>.tres`, and the
scene sync points the weapon's `AttackRange` / `AttackRangeGround` / `AttackRangeAir`
node at that resource as an `ExtResource` — no scene carries a range cylinder of its own
any more. A mapping `reach:` on a weapon whose scene has one locally declared
`AttackRange` replaces it with the split pair.

### kind: SpeedLibrary

The **speed ladder**: every authored speed — a piece's `movement.speed`, an emission's
shorthand `speed:` and a phase's `motion.speed` — NAMES a class, and the value lives only
here. A bare number is refused, and so is a name the ladder does not have. Retuning a class
is one edit, and every piece and emission in it follows on the next import.

The ladder is ONE doc, `gdd/movement/speed_classes.md`. Its `speeds:` mapping is class name
(UPPER_SNAKE) to world units per second; a second SpeedLibrary doc is an error.

```yaml
# file: gdd/movement/speed_classes.md
kind: SpeedLibrary
speeds:
  ZERO: 0          # a piece or emission that does not move
  SLOW: 1.65
  SUPERSONIC: 30
```

The registry swaps each name for its number right after every doc is registered and before
anything is validated (`SpecRegistry._resolve_speed_classes`), so the rules, generators and
scene sync read a number exactly as they did when docs carried one, and scenes still store
world units per second. `aerial.orbit_speed` is a class too; nothing else is: `min_speed`,
`launch_speed_ratio` and the `*_speed_ratio` chassis fractions stay numbers.

## Calibration rules and the `exceptions:` block

Beyond per-key validation there is a second pass, `tools/spec_import/spec_rules.gd`,
which checks relationships **between** a piece's numbers. The two ask different
questions: validation asks "is this value well-formed" and every answer is local
to one key, while a rule asks "do these numbers make a unit", which never is —
an aggro radius is fine on its own and wrong beside a longer weapon reach.

A rule yields one of five verdicts per piece:

| Verdict | When | Result |
|---|---|---|
| `ACCEPTED` | the rule holds | silent |
| `EXCEPTIONAL` | violated **and** the doc declares it | listed in the run summary, with the stated reason |
| `UNACCEPTED` | violated, undeclared | hard error; nothing is written |
| `STALE` | declared but not violated (or not applicable) | hard error |
| `INCOMPLETE` | an `ASSET` rule's slot is unfilled, undeclared | listed in the run summary with its `AssetState` (`PLACEHOLDER`/`MISSING`); never an error |

The summary also reports the **combat model's staleness**: the armed units (a doc with
`movement:`, a `weapons:` list and an energy cost) the shipped `resources/bots/combat_model.json`
was never fitted on, and the types it knows that are no longer armed units. An unknown unit
drops every producer that can train it onto the demand map, so a balance pass that adds or arms
a piece should end with `tools/combat_model/regenerate.sh` (gdd/systems/ai/macro-learning.md §1).
Reported, never an error: the bot plays on meanwhile.

`ASSET` rules (`has_mesh_visual`, `has_voice_lines`, `has_death_sound`) are the one
severity where an undeclared violation is not a failure: a missing asset crashes
nothing, so it is reported rather than refused. A waiver makes the slot `EXEMPT`.

Three verdicts rather than two because a roster with no exceptions to its norms
is a roster with no artillery in it. You declare a departure in the doc's own
frontmatter, beside the numbers it justifies:

```yaml
exceptions:
  reach_within_vision: >-
    Artillery. Out-ranging its own sight is the mechanic — it is why spotters are
    worth fielding, and why killing the spotter answers the battery.
```

`STALE` is what keeps that honest. Without it a declaration outlives the value it
waived, and the block becomes a list of things that used to be true — which still
reads as deliberate, and is worse than no list. So a declaration costs something
at both ends: write it when you break the norm, delete it when you stop. An
unknown rule id and a blank reason are errors too — a waiver naming nothing
waives nothing, and the sentence saying why *is* the deliverable.

**STRUCTURAL rules cannot be declared away.** Some rules are not norms at all:
they describe a piece that cannot physically do its job, like a fixed wing whose
turning circle is wider than its weapon's reach (it can never be both pointed at
a stationary target and close enough to fire — it orbits at arm's length
forever). Waiving that would only record the intent to ship something broken.
The dividing line is "is this a balance opinion, or is it geometry".

| Rule | Severity | The norm |
|---|---|---|
| `turn_radius_within_reach` | structural | a fixed wing can turn tightly enough to point at what it shoots |
| `grounded_air_attack_not_melee` | structural | a ground unit that shoots at aircraft does so at range |
| `detection_within_vision` | normative | a piece detects stealth no further than it can see |
| `reach_within_vision` | normative | a piece can see what it shoots at |
| `bio_pivots_in_place` | normative | infantry turns on the spot rather than swinging round |
| `braking_outpaces_acceleration` | normative | a ground vehicle stops harder than it starts |
| `aerial_weapons_not_melee` | normative | a fixed wing strikes from range rather than by ramming |
| `clip_outlasts_reload` | normative | a clip takes longer to refill than to empty |

Two of them exist mainly to keep a set NAMED rather than to forbid anything.
`reach_within_vision` is how the spotter-dependent pieces announce themselves,
and `aerial_weapons_not_melee` is how a rammer does — a FLYING unit with a
melee-reach weapon **is** the dive attack, which is why `Weapon.is_melee_ranged()`
is derived from reach — the authored `dive_attack` export and the `dive:` doc key
that fed it are both gone.

The design rationale for each rule, including the counterexamples that shaped
them, is in `gdd/unit-calibration.md`. Checked by running the importer, not by a unit test.
