# Simulation tests

*Design note for [Dissent Horizon](../../../CLAUDE.md). Rules here are authoritative; CLAUDE.md
carries only the pointer.*

> The grammar, the parser, the arena builder and the runner all exist; `sims/` holds the
> specs. What is not built carries a `TODO`. §Running one says how to run them.

A **simulation test** is one authored situation plus the claims it must satisfy:

- *two units fight; after 10 seconds both are dead;*
- *a truck drives at a unit that is shooting it; it crushes it and survives;*
- *A's two tanks and five soldiers beat B's three APCs.*

## A simulation test asks about DESIGN; a regression test asks about the software

**This is the line, and it decides everything else in this note.** A simulation test asks
whether the game is *balanced and behaves as designed* — an answer allowed to change when a
stat changes, and whose honest form is often a rate rather than a yes. A regression test asks
whether the software is *still correct*, and its answer must not move unless someone broke
something.

Three rules follow:

1. **Simulation tests do not run in GUT, and nothing under `tests/` is one.** GUT is the gate —
   what CI blocks on, once CI exists. A balance question failing there would train everyone to
   ignore red. Specs live in `sims/`, editor-authored scenarios in `scenes/scenarios/test/`,
   and both are driven by `tools/simulation/`.
2. **If a thing driving a live scenario is checking programmatic stability, it is a REGRESSION
   test and belongs in GUT** — a nav path that must resolve, a command that must not deadlock,
   a scene that must load. The word "simulation" describes the environment, not the category.
3. **The grammar's own parser and validator ARE unit-tested**, in GUT, like any other code.
   The parser is software; the simulations it parses are not.

> **This narrows `~/.claude/CLAUDE.md` §6.2**, which calls a simulation test "a regression test
> in a simulated environment" and files it under testing. Here the two are separate categories
> with separate homes and separate consequences for a red result. Stating the exception rather
> than quietly diverging (§12).

## One spec is one run

**A spec describes a single run. Repetition, seeds and tolerance are the runner's.** A spec
names no trial count and no pass rate; the batch runner executes it once or two hundred times
over a seed range and the file does not change between those.

`run.seed` is the exception that proves it: it is **the seed for this one run**, not a sampling
policy. Omitted, the runner draws one and records it in the result — so an interesting outcome
is always re-runnable, and a sweep is the runner passing a different seed each time. Tolerance
("the truck wins at least 9 times in 10") is a batch-config key and never appears in a spec,
because a threshold is a statement about a sample and a spec has no sample in it.

## The file

Specs live under `sims/`, and **a sub-directory is part of a spec's id**:
`sims/bot/targeting/crush_a_counter.sim.yaml` is `bot/targeting/crush_a_counter`, which is
what `spec=` selects by (a bare file name still matches). The decision simulations are filed
under `sims/bot/<domain>/`, one directory per decision, and a spec there must have a thinking
slot or it is refused. A top-level `needs:` names what a spec is waiting on — a read or a
migration step not built yet — so its red run is reported as WAITING, not as a failure
([ai/decision-sims](../ai/decision-sims.md) §Organising the state space). Unknown top-level
keys are refused (they used to be ignored).

`sims/<name>.sim.yaml`, one spec per file, **the file name is the test id**. Parsed by
`SpecFrontmatter.parse_yaml` — already exposed for bare (unfenced) lines, and its subset
already covers nested mappings, sequences of mappings, flow collections and `|` block scalars.

Rejected alternatives, both for reasons that bit before:

- **A `.tscn` generated by a script**, which is what `tools/generate_test_scenarios.gd` does
  today. It inverts `~/.claude/CLAUDE.md` §10 — the generated artifact becomes the thing you
  hand-edit. The arena is built at RUNTIME instead, so there is no derived artifact to drift.
- **A gdd doc with `kind: simulation` frontmatter.** Discovery in `gdd/` is by the `kind:` key,
  so a new kind means teaching the spec importer about a file it has no business importing.

**A spec that does not parse is a FAILED spec, never a skipped one.** This is the
`test_SuiteIntegrity` lesson in a second place (CLAUDE.md §A skipped test file is invisible):
the runner enumerates `sims/*.sim.yaml` and reports an unparseable file as a failure naming the
offending line. YAML forbids tab indentation and Godot has twice reindented files it merely had
open (CLAUDE.md §Regenerating data), so this is a live hazard — and the parser already returns
that exact error.

## The worked example

```yaml
description: |
  A stock truck is unarmed; its answer to infantry is to drive over them. The claim has two
  halves and both matter: the infantry dies, AND the truck is not whittled down on the way in.
setting: { kind: flat, size: 30 }
given:
  A:
    with:
      armyA:
        of:
          - { piece: cl_mechLight_dominionGen, count: 1 }
        at: west
        facing: east
        orders: [ { attack_move: { to: B.armyB } } ]
  B:
    with:
      armyB:
        of:
          - { piece: cl_bioLight_antiLight, count: 1 }
        at: { from: A.armyA, distance: 14, bearing: east }
        facing: east
        orders: [ { attack: { target: A.armyA } } ]
run: { for: 10s, seed: 91125 }
expect:
  - { of: B.armyB, check: dead }
  - all:
      - { of: A.armyA, check: alive }
      - { of: A.armyA, check: hp_fraction, at_least: 0.5, when: always }
```

A mixed engagement is the same shape with longer `of:` lists, and `settings` where a side
should think for itself:

```yaml
given:
  A:
    with:
      spearhead:
        of:
          - { piece: cl_mechMedium_antiLight, count: 2 }
          - { piece: cl_bioLight_antiMech, count: 5 }
        at: west
        formation: line
        orders: [ { attack_move: { to: B.column } } ]
  B:
    with:
      column:
        of: [ { piece: an_mechStrong_transport, count: 3 } ]
        at: east
        formation: line
    settings:
      difficulty: MEDIUM
```

## `setting` — the ground

```yaml
setting: { kind: flat, size: 30 }
```

The arena, and nothing else. **A generic arena rather than a shipped map**, because a spec must
mean the same thing wherever it runs and a shipped map's terrain is authored content that moves.

> **TODO — only `kind: flat` is planned.** A spec that needs a slope, a choke or water has
> nowhere to say so. The extension is more `kind`s, not a map path.

## `given` — commanders, their groups, their settings

```yaml
given:
  A:
    with:
      armyA: { … }
      armyA2: { … }
    settings:
      difficulty: MEDIUM
```

Three levels, each meaningful:

- **The immediate children of `given` are commander slots** (`A`, `B`, …, mapped to commander
  ids in declaration order; `NEUTRAL` is id 0).
- **`with` holds that commander's GROUPS** — the unit of ordering, targeting and assertion. A
  group holds one piece or fifty.
- **`settings` configures the commander itself.** `difficulty` defaults to **`PASSIVE`**, and
  in a spec that means **INERT**: the slot's `BotBrain` is switched off, so a force does only
  what its orders say. A slot that should think names any other tier and gets the real brain.
  `faction` names a faction scene (the Colonial one by default).
- **A THINKING slot may carry five more keys** — a decision simulation's levers
  ([ai/decision-sims](../ai/decision-sims.md) §Grammar extensions), each refused on an inert
  slot: `vision: full` (no `Fog` for the commander, so it sees the whole arena through the
  same perception code), `energy` and `dominion` (its stockpiles; zero otherwise), `config`
  (a mapping of `BotDifficulty` field overrides, validated as a `PlayerSlot`'s are), and
  `consider: { structures: […], units: […] }` (the only piece types the bot may build or
  train; a list left out means all of them). **A thinking slot's personality is zeroed** —
  `personality_spread` and `decision_temperature` are 0 unless `config` sets them — so a
  decision is the argmax and a run reproduces.

> **In a spec, `PASSIVE` is a narrowing of the engine's tier, and it has to be.** `Scenario`
> attaches a thinking `BotBrain` to every bot slot, and PASSIVE does *not* make it inert —
> the tier means "minimally active, and never attacks", so a passive bot still builds, trains,
> defends itself and **re-tasks its idle units**. A controlled measurement cannot have a second
> decision-maker in it. `SimArena._silence_unthinking_brains` sets `BotBrain.active = false`,
> which is the flag that genuinely freezes a commander and whose own doc reserves it for
> "a scenario that genuinely wants a frozen commander".
>
> This was not theoretical: a stock truck ordered to drive at an enemy had its order cleared on
> the first think pass, two seconds in, and stood still while it was shot to death. Nothing in
> the spec could be read to explain it — which is exactly why the default must be inert.

**Groups are fenced behind `with` so that every child of it is a group, with no exceptions to
learn.** The alternative — groups as direct children of the slot, alongside a reserved
`settings` key — makes one key secretly not a group, which is the one thing a reader could not
tell by looking, and it would collide the day someone names a group `settings`.

**A group is referenced as `<slot>.<group>`, always qualified.** `A.armyA`, never `armyA`:
whose it is, is half of what a reader needs at the use site, and unqualified names would make
splitting a force into `armyA1` / `armyA2` a rename with action at a distance.

**Grouping is the spec's only structural knob, and it is how intent is expressed.** The same
nine units are one army or three, and that choice *is* the experiment — an army attacking
`A.armyA` versus one attacking `A.armyA1` while another takes `A.armyA2` is the difference
between a brawl and focus fire, written as the difference between one group and two.

### Group keys

| Key | Meaning |
|---|---|
| `of` | list of `{ piece, count }`; `count` defaults to 1. Mixed pieces are ordinary |
| `at` | placement — an anchor, another group, or a `from`/`distance`/`bearing` offset |
| `facing` | an anchor or a group reference, never degrees |
| `formation` | `line` \| `ring` \| `cluster`; arranges the whole group, mixed pieces included |
| `orders` | commands issued to **every member** at t=0, as one queue; an entry with `after:` is issued later (§Timed orders) |

### Placement is symbolic, never a world coordinate

A spec must read the same on any arena, so no block holds a world position.

- **Anchors** are arena-relative: `center`, `north`, `south`, `east`, `west`, and the diagonals.
  They resolve against the arena's extent, so the same spec on a bigger arena spreads out.
- **`from` / `distance` / `bearing`** offsets a placement from another group or an anchor;
  a group resolves to its centroid. `distance` is in **world units** — the unit weapon ranges
  are stated in (§2.2), not cells and not a fraction of the arena.
- **`formation`** is `line` | `ring` | `cluster`, laid out as deterministic geometry at a
  fixed `SimArena.FORMATION_SPACING`. It does NOT reuse `StartingFormation`, which reads
  fixed authored patterns (`pair`, `wedge_3`) and cannot arrange an arbitrary count; nor
  `SU.get_nonoverlapping_points`, which probes the live physics world and so needs a Map
  already in the tree. Deterministic is also the better answer here: an experiment wants the
  same starting layout every run rather than a seeded shuffle of it.

**Distances are absolute and placements are relative, deliberately.** The gap between two
groups is what a duel is *about* — it decides who shoots first. Where they both stand is not.

## Orders, and what a target means

An order names a command and its argument. Which argument a command takes is the command's own
business (`move_command.gd`'s `requires_position()` already draws that line), so the grammar has
two argument kinds and one rule for each.

### Every order names its argument with the same two keys

`target:` and `near:`, whatever the verb — one vocabulary, so a reader never has to remember
which word this particular command wanted.

| Key | Means | Accepted by |
|---|---|---|
| `target:` | the thing, or the exact place, the order is aimed at | every command |
| `near:` | a place BESIDE that thing rather than on it | positional commands only |

Setting both is a validation error, and so is `near:` on an entity-valued command — `attack`
names an entity, and accepting a place there would quietly turn a kill order into a walk.

**The distinction earns its place on the truck.** Running infantry down needs `target:` — drive
at the point itself. Marching an army up to a position needs `near:`, which stops at the
referenced group's own edge (its radius plus `SimArena.APPROACH_STANDOFF`) instead of driving
into it. A `near:` that names an anchor rather than a group has no extent to stand off from, so
there it means the same as `target:`.

> The key was `to:` until 2026-09-12. A spec still using it gets an error naming the
> replacement rather than a shrug.

### `target:` is LIVE; `near:` is a snapshot

**A `target:` that names a group carries the ENTITY**, whatever the command — `attack` and
`move` alike. `CommandMessage.position` reads `target.global_position` whenever a target is
set, so the destination tracks the unit for free, and a target that walks away is still the
thing being driven at.

That matters most for the command that looks least like it needs it: `move: { target: G }` is
how an unarmed piece attacks, and snapshotting the position sent the truck to a patch of empty
ground the infantry had already left. Aiming at a *place* where a *thing* was is the bug the
two key names exist to keep apart.

**`near:` is the other half.** It names a place, so it resolves once, at issue time — and so
does a `target:` built as an OFFSET from a group (`{ from: B.armyB, distance: 4, bearing: east }`),
because that describes a place derived from a group rather than the group. Only the bare form,
`target: B.armyB`, is the thing itself.

**A target that leaves the play space takes its order with it.** A garrisoned entity is off the
scene tree and reports position (0, 0, 0), so an order still holding it would drive its actor at
the map's centre — which is what the stock truck did after capturing what it was aimed at. The
rule, and the two limits on it, live where the command tick owns them:
[`../commands/the-command-tick.md`](../commands/the-command-tick.md) §A target that LEAVES THE
PLAY SPACE. **Found by `spaced_antimech_vs_truck`** — the first thing these specs caught that
no unit test was looking for.

### An entity `target:` expands over a group

A `target:` names a group. **An order against a group expands to a QUEUE of that command, one
per member, in the group's declaration order** — `attack: { target: A.armyA }` is *"kill
everything in armyA, in the order it was written"*. Every member of the ORDERING group receives
that same queue.

Two things fall out, and both are wanted:

- **Focus fire is the default**, because every attacker works the target list in the same order.
  Spreading fire is expressed by splitting the defenders into groups and giving each attacking
  group its own — which is exactly the `armyA1`/`armyA2` distinction above, and the reason the
  expansion is declaration-ordered rather than nearest-first. Nearest-first would make the
  spec's meaning depend on geometry the author is also varying.
- **Attrition resolves itself.** A queued command against a dead entity is dropped by the
  existing command tick, so the queue is a priority list, not a script that stalls.

Each entity resolves at issue time and the command holds it, exactly as a player's right-click
does — so a target moving, dying or changing hands is the simulation's business.

To name ONE entity, or part of a mixed group, use the selector form:

```yaml
orders: [ { attack: { target: { of: B.column, piece: an_mechStrong_transport, pick: nearest } } } ]
```

`pick` is `nearest` | `furthest` | `first` (declaration order) and `piece` filters a mixed
group. Without `pick`, the target is the whole (optionally filtered) set and expands as above.

### Where a place resolves to

`near:`, and a `target:` that names an anchor or an offset, take the same expression as `at:`
and resolve **at issue time**. A group used as a place means its centroid.

So `attack_move: { near: B.armyB }` means *march up to where that group is standing now*,
stopping at its edge.

### Timed orders: `after:`

```yaml
orders:
  - { move: { target: { from: B.target, distance: 7, bearing: north } } }
  - { move: { target: { from: B.target, distance: 7, bearing: south } }, after: 1s }
  - { move: { target: { from: B.target, distance: 7, bearing: north } }, after: 2s }
```

**An order entry may carry `after:`, a positive duration in seconds** (built 2026-10-03). The
orders without it are the opening queue, issued at arming as before.

- **All of a group's orders sharing one `after:` are issued together, on the first tick at or
  past that time, as ONE fresh queue.** That queue REPLACES whatever the group was doing,
  the way a player's right-click does. A timed order is a reroute, not an append.
- `after:` at or past the `run` window is refused: it would never be issued.
- Time counts from arming, like the window itself.

It exists for the rocket-evasion specs, where the claim is about a target that changes course
after a shot is away (`warlord_vs_*_jinking`): a queue of moves cannot say WHEN the course
changes, only where. `SimulationScenario._on_tick` is the hook; `SimArena` issues each batch
from it.

## `run` — a window, not a race to a verdict

```yaml
run: { for: 10s, seed: 91125 }
```

**The simulation plays the full window and stops.** It does not end early when every check has
resolved, because at-end and safety checks are only meaningful over the whole window — a run
that stopped as soon as the truck was alive would be asserting nothing.

Time is authored in **seconds** everywhere. The physics rate is an engine detail and must never
become a unit (§2.2): the tick conversion is derived from the project's physics-rate setting
(`TimeUtils`) at the boundary, once. `SimulationExpectation.deadline_ticks` is the existing violation, and §What
exists today says what happens to it.

## `expect` — leaf checks, and a boolean tree over them

```yaml
expect:
  - { of: B.armyB, check: dead }
  - all:
      - { of: A.armyA, check: alive }
      - { of: A.armyA, check: hp_fraction, at_least: 0.5, when: always }
```

**The top-level `expect` list is an implicit `all`.** Inside it, `all:`, `any:` and `not:` nest
freely over leaf checks and over each other. `not:` is there so the algebra is complete —
without it an author eventually needs a negation the check table cannot spell.

### A leaf carries the temporal mode; the tree never does

**A temporal mode is a FOLD over the leaf's per-tick truth** — an operator and a window. That
is the whole of it, and all three modes are one mechanism:

| Mode | Written | Fold | Window |
|---|---|---|---|
| **At end** | *(default)* | sample | the final tick |
| **Liveness** | `by: 8s` | `or` | from the start until it is true, else until `8s` |
| **Safety** | `when: always` | `and` | every tick of the run |

So a safety leaf accumulates, starting true:

```gdscript
# every physics tick, for each armed safety leaf
verdict = verdict and leaf.evaluate()
```

and a liveness leaf is the same shape with `or` and an early exit at its deadline. **A new
temporal mode is a new (operator, window) pair, never a new branch** (§1.2).

`when:` and `by:` together is a validation error.

**The fold is per LEAF. Every leaf is therefore determinate by the end of the run, and the tree
is evaluated ONCE, at the end, over those fixed verdicts.** That is what lets an `any:` hold a
safety leaf and an at-end leaf together without the combinator needing a temporal meaning of its
own.

> **The alternative, not taken: folding the CLAUSE per tick** — evaluating a whole `any:` every
> tick and `and`-ing the results. It is a different and stricter claim (`and` over ticks of
> `P or Q`, rather than `verdict(P) or verdict(Q)`), and it requires asking an at-end check what
> it says at tick 5, which is a question that has no meaning: "when the window elapses" is the
> leaf's entire definition. Folding leaves keeps every mode's meaning local to the leaf that
> declares it.

**At-end is the default because it is what a claim about an outcome means.** Under the
liveness-only `SimulationExpectation`, *"the truck survives"* is inexpressible: a check that
passes the first tick it is true passes at tick 1, before anything has happened.

> **The accepted pitfall: this cannot express "A and B were true AT THE SAME TICK."** The tree
> composes final verdicts, not live truth. **TODO** — if simultaneity is ever needed it is a
> composite LEAF check, not a temporal combinator.

### Why the safety mode earns its place

`when: always` is the per-tick check, and it is not sugar for an at-end check. Four things only
it can say:

- **The claim is about the PATH, not the destination.** "The truck survives the approach" as an
  at-end check passes on a run where the truck dropped to 5% and was then repaired, healed or
  garrisoned back up — a run that demonstrated the opposite of the claim. A floor that held
  throughout is the claim actually being made.
- **Non-monotonic state is invisible at the end.** Ownership flips back (capture, recapture),
  garrison occupancy flips back, a status effect lands and expires. "B never held my truck" and
  "it was never picked up" have no at-end form at all.
- **It guards the measurement itself.** "Never idle", "never acquired a neutral as a target",
  "never left the arena" are cheap assertions that the run measured the thing the author thought
  it did. A balance number taken from a run where a unit was stuck for four seconds is worse
  than no number.
- **It retires a bespoke-Condition pattern.** `ConditionUnitHasNoCommandFor` is a hand-rolled
  per-tick streak check written because there was no general way to say a negative about
  behaviour over time. That it exists is the evidence the need is real.

The cost is honest and worth stating: **a safety check has thirty chances per second to trip
where an at-end check has one**, so under a non-deterministic simulation it is the mode most
likely to produce a false red. That argues for using it on robust properties — an hp floor with
margin, ownership, "no command" — and not on tight positional ones.

> **TODO — `always` cannot be scoped to a window.** What an author usually wants is "always
> after the opening 2 seconds", ignoring the boot transient (spawn settling, the first navmesh
> sync). `when: always, after: 2s` is the extension; the grammar reserves `after:` for it, the
> same key timed orders use.

### The check vocabulary

Every leaf takes `of:` (a group reference) and optionally `piece:` (narrowing a mixed group).

| Check | Arguments | True when |
|---|---|---|
| `alive` | `exactly` / `at_least` / `at_most` | that many of the selection are alive (default: **all** of them) |
| `dead` | same | (as above, for dead ones) |
| `hp_fraction` | `at_least` / `at_most` | every living member is within that fraction of its max hp |
| `owner` | `is: <slot>` | every living member belongs to that slot — capture outcomes |
| `distance_to` | `target: <group>`, `at_least` / `at_most` | the two centroids are that far apart |
| `command` | `is: <CommandName>`, optional `target: <group>`, optional `near: <group>` + `within: N` | every living member's current command is that one — and, when asked, is aimed at a piece of `target`, or has its destination within N of `near`'s centroid |
| `idle` | — | no member holds a command |
| `garrisoned_in` | `host: <group>` | every member is inside that host |
| `hit_rate` | `target: <group>`, `at_least` / `at_most` | of the shots the group fired that have settled, that fraction landed on the target group (§Counting shots) |

**Bot-state checks** ask what a THINKING slot decided, from its own records, and take `slot:`
in place of `of:` (`claimed` keeps `of:`, a claim being about units; `believes` takes both).
Each is false until the slot's brain has built its managers — a decision not yet made does not
pass. The rule for them, and the situations they were written for, are
[ai/decision-sims](../ai/decision-sims.md).

| Check | Arguments | True when |
|---|---|---|
| `posture` | `slot`, `is: ATTACK / MASS / DEFEND` | `BotMilitary.current_posture()` is that |
| `objective` | `slot`, `near: <group>`, `within: N` | the army's objective lies within N of that group's centroid |
| `ordered` | `slot`, `kind: <actuator verb>`, optional `piece`, `at_least` (default 1) | the actuator ISSUED that many orders of that kind (`BotUsageLog.actions`, a ledger by type) |
| `refused` | `slot`, `kind`, optional `piece`, optional `cause: <PreconditionFailureCause>`, `at_least` | the actuator refused that many, with that cause when named |
| `chosen` | `slot`, `domain: <choice domain>`, `piece` | the piece won a scored decision in that domain (`BotUsageLog.choices`) |
| `considered` | same | the piece was scored at all — the audit's "not aware" versus "not worth it" |
| `claimed` | `of: <group>`, `holder: <claim owner>` | every living member is held by that manager (`BotClaims`) |
| `believes` | `slot`, `of: <group>`, `exactly` / `at_least` / `at_most` | the slot's blackboard believes that many of the group (all, with no count) |

**A check with no count argument quantifies over ALL of the selection.** One axis, not a
separate `quantifier:` key. A new check is a new row in that table, never a new branch (§1.2).

### Counting shots

**`hit_rate` measures a WEAPON, not a fight** (Alex, 2026-10-03). It counts the emissions the
group's pieces fired (`ActionTracker.CUE_EMITTED`) and how many landed on a piece of the target
group (`Payload.paid_out`), and asks whether the fraction is in the band. Killing is a different
question: it is the shooter's damage rate, and a cheap unit is not expected to kill a target
alone before it escapes. So a projectile is tuned by how often it hits, never by whether its
target died.

- A shot counts once its emission has LEFT THE GAME (`SimShotLog`): one still in flight at the
  end of the window is neither a hit nor a miss.
- A shot hits if any of its payouts reached a member of the target group, including a member
  since destroyed (the roster keeps every placed piece's instance id).
- A run that settled no shot fails the check: a rate over nothing is not a measurement.
- The check REPORTS what it counted: `measured` in the JSON result (and in the printed line)
  reads "7 of 9 shots hit". `SimulationCheck.measurement` is the general hook; a check that
  only has a verdict leaves it empty.

Where the table cannot reach, the escape hatch is the scenario `Condition` module —
`{ condition: ConditionScoutCoverage, commander_id: 1, …, by: 100s }` — but it is not the
primary route, because the two address different things. A `Condition` scopes by commander id,
piece type and region: it describes a *population*. These checks describe *this group, the one
this spec placed*. Widening `Condition` to take a group reference would push a simulation-only
concept into the mission-scripting layer that ships in the game.

## Validation is total and loud

The importer's posture, for the importer's reason — a fuzzy match here silently measures
something nobody asked about. Abort the spec, name the key: an unknown slot or group reference,
a `piece` not in `EntityIds`, a `pick` on a check, `when:` with `by:`, an unknown check name, a
placement cycle (`A.x` placed from `B.y` placed from `A.x`), or a group with an empty `of`.

## Running one

```bash
# every spec in sims/, once each
godot --headless --path . --fixed-fps 30 tools/simulation/run_sims.tscn

# one spec, ten seeds, with the full result as JSON
godot --headless --path . --fixed-fps 30 tools/simulation/run_sims.tscn -- \
    spec=duel_builder_mirror trials=10 seed=1 out=/tmp/sims.json
```

`--fixed-fps 30` detaches the main loop from wall time, so a 10-second spec takes about a
second rather than ten. It is not optional for a batch.

### Watching one play out

```bash
godot --path . tools/simulation/run_sims.tscn -- spec=spaced_antimech_vs_truck hold=5
```

**Drop both `--headless` and `--fixed-fps`** — the first is what suppresses the window, the
second is what makes the run finish before you can look at it. Narrow to one spec, because the
runner otherwise marches through every one of them. `hold=<seconds>` keeps the window up after
the last window elapses, which is otherwise the moment it vanishes.

**Everything a watcher needs is already there and costs the framework nothing**: every slot in
a spec is a bot, so `Scenario` takes the session for a spectator one and supplies its own
pan/zoom camera, the resource readout and the fog toggles (No Fog / Bot N POV). There is no
human rig to make current, which is exactly the condition that path tests for.

Two things an arena adds for the watcher only, both cosmetic and both absent headless:

- **A stand-in ground plane** (`SimArena._ground_plane`). An arena has no `TerrainData` and so
  no baked visual surface, and without this a watched run shows units floating in a void.
  Nothing reads it — passability is the heightmap and `TerrainGrid`, and it is deliberately
  kept out of `navigation_mesh_source_group` so nobody infers otherwise.
- **A camera framed on the arena** (`SimArena.CAMERA_FIT_FRACTION`). The spectator camera's
  authored orthographic size is 15 world units, sized for a player's opening view of a real
  map; an arena is routinely wider, so a watched run would otherwise open with its units off
  the edge of the screen.

To capture frames instead of watching live — useful when a run is too fast to follow, or to
show someone what happened — add `--write-movie`, which works because it does not need
`--headless`:

```bash
godot --path . tools/simulation/run_sims.tscn --write-movie /tmp/run.png \
    --fixed-fps 30 --quit-after 240 --resolution 1280x720 -- spec=duel_builder_mirror
```

It writes `run00000000.png`, `run00000001.png`, … `--quit-after` counts FRAMES, so pick a
number past the opening seconds. There is no input and no OS cursor in those frames — they show
the world, not the HUD's interactive state.

`trials` and `seed` are the RUNNER's, never a spec's. Trial *k* runs at `seed + k`, and the
seed is recorded with every trial — so a 7-of-10 result can be reopened at the seed that lost.
A spec naming no seed gets a random one, recorded the same way.

The summary ends with three counts — passing, failing, and **waiting on something not built**
(a spec with `needs:` that did not pass; one that passes with the key still set says so, so the
key is dropped).

**The exit code is 1 only when a spec failed to PARSE or BUILD**, never when an expectation
came out false. A design claim being false is a finding; a runner that exited non-zero for it
would end up wired into a gate, which is the whole thing this note separates.

The editor-authored scenarios have their own runner, `tools/simulation/run_scenarios.tscn`,
for the same reason and with the same posture.

**Nothing in the GUT suite runs a spec.** What GUT covers is the parser, the validator and the
fold — `tests/test_SimSpec.gd` and `tests/test_SimulationCheck.gd` — which are pure: a spec in,
a validated structure or a list of errors out, no engine and no scene tree (§7). Only the arena
builder and the evaluator touch the engine.

## Determinism is deferred

Steps 1-3 of the seeded-randomness task are done — `Scenario.rng_seed`, `seed_simulation()`,
every gameplay draw through a seeded generator — and the residual divergence is **not a draw, it
is a race** in Godot's RVO avoidance thread pool: sub-unit positional drift that compounds. On
one seed, two runs were bit-identical to tick 1230 and then parted.
[`../ai/selfplay-harness.md`](../ai/selfplay-harness.md) §Determinism has the numbers.

**Nothing here waits on that**, because a spec is one run and the runner owns the sample. A
claim with margin — "both die inside ten seconds", when they die in six — is sound today; a
claim on a knife edge is a rate, which is what the runner reports anyway. Keep the margin in the
`run` window rather than in the claim.

## The pieces

| File | Does |
|---|---|
| `tools/simulation/sim_spec.gd` | parses and validates a spec. **Pure** — no engine, no scene tree |
| `tools/simulation/sim_piece_catalog.gd` | piece id → scene path, read straight from `tools.json` |
| `tools/simulation/sim_arena.gd` | builds a runnable `SimulationScenario` from a spec |
| `tools/simulation/sim_group_roster.gd` | what was placed: group → entities, and the slot ids |
| `tools/simulation/sim_check_library.gd` | the check vocabulary, as predicates over a roster |
| `tools/simulation/run_sims.gd` | the runner: trials, seeds, JSON |
| `scripts/scenario/simulation_scenario.gd` | the shared runtime: window, folds, report |
| `scripts/scenario/simulation_check.gd` | one leaf and its fold |
| `scripts/scenario/simulation_expectation.gd` | the editor-authored route, compiling to a leaf |

**`SimPieceCatalog` reads `tools.json` as a FILE rather than going through `Tool`'s registry.**
Touching that registry instantiates every tool scene in the game, and a file-scope reference to
it from a test has already taken out a whole GUT run once (CLAUDE.md §A file-scope `preload` of
an entity scene in a test can poison the whole run). A spec parser has no business booting
content.

**They were `TestScenario` / `TestExpectation`, run by `tests/test_BotTestScenarios.gd`, until
2026-09-12.** The rename and the move out of GUT are the same correction: these ask design
questions, and one of the three was `pending()` for flakiness — which is what a design question
looks like when it is made to sit in a regression gate. Outside the gate all three pass and the
flaky one is reported as flaky rather than hidden. `scenes/scenarios/test/` keeps its name
because it also holds genuine regression fixtures (`mesh_terrain_*`, `nav_straight_line`) that
GUT does drive.

**The runtime was widened, not cloned.** A spec-driven arena and an editor-authored scene are
two authoring routes to one thing — a scenario with checks and a window — so implementing the
spec route as a sibling of `SimulationScenario` would have been the mistake §1.3 names.
`SimulationScenario` holds `Array[SimulationCheck]` and a run window; `SimulationExpectation`
is one producer of a leaf (always LIVENESS, which is what `deadline_ticks` has always meant)
and `SimArena` is the other. The three editor-authored scenes still pass unchanged.

**The window is measured from ARMING, not from `_ready`.** Arming waits on the first navmesh
sync, which is genuine boot rather than simulated time, and a deadline eaten by it would be
measuring the engine instead of the game.
